#+TITLE: LLM Wiki vs RAG
#+FILETAGS: :comparison:llm:rag:wiki:

* Summary

Both Retrieval-Augmented Generation (RAG) and the [[id:2714125c-2dc8-447e-869c-0a3f35916903][LLM Wiki Pattern]]
let an LLM "remember" content beyond its context window, but they
solve different problems. RAG retrieves *raw chunks* at query time; an
LLM wiki holds *synthesised pages* whose content was already curated
by the LLM during ingest.

* Side-by-side

| Aspect            | RAG                                  | LLM Wiki                              |
|-------------------+--------------------------------------+---------------------------------------|
| Storage unit      | Document chunks + vectors            | Org-mode pages with =:ID:= drawers    |
| When LLM thinks   | Once at query                        | Once at ingest, again at query        |
| Cross-references  | Implicit (semantic similarity)       | Explicit (=[[id:UUID]]=)              |
| Compounding       | Linear in #docs                      | Non-linear via link graph             |
| Retrieval cost    | Vector similarity over corpus        | Read =index.org= + follow links       |
| Best when         | Many docs, infrequent updates        | Curated domain, incremental learning  |
| Worst when        | Need durable cross-doc synthesis     | Volume too high to curate per-source  |

* When to pick which

- *RAG* for: company knowledge base over 10k docs, customer-support
  bot, "summarise this PDF" use cases.
- *LLM Wiki* for: personal study notes, long-running research project,
  domain you want to *learn* (not just look up).

This distro ships the LLM Wiki side. For RAG over the same content,
nothing stops you from running ~M-x org-roam-node-list~ → embed via
gptel-context, but that's an exercise.
