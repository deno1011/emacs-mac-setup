* Manual
** The Compact File Model
This setup keeps the GTD system small on purpose.

- inbox.org: raw capture, brain dumps, and anything not clarified yet.
- gtd.org: next actions, projects, waiting-for, someday/maybe, tickler, and reviews.
- calendar.org: dated commitments and true deadlines.
- archive.org: completed or cancelled items after archiving.
- gtd/*.org: GTD assistant skill manuals for daily planning,
  scheduling, inbox clarification, weekly review, and horizons. The
  setup also seeds split GTD files under gtd/ for users who prefer
  separate operational files.

Reference material can live outside GTD, for example in your wiki or
notes. Only create another GTD file when it solves a real review
problem.

** The Full GTD Loop
Use this system as a loop, not as a place to park vague intentions.

1. Capture everything unfinished into inbox.org with C-c c i.
2. Clarify one inbox item at a time until the inbox is empty.
3. Organize clarified outcomes into the right trusted bucket.
4. Reflect daily and weekly so the lists stay current.
5. Engage from the agenda views by context, time, energy, and priority.

The empty top-level sections below this manual are intentional landing
zones. Capture and refile commands need stable headings. They begin
empty because your real system should contain your real actions, not
installer sample tasks.

** Split GTD Files
The compact default system uses this =gtd.org= file as the primary
operational file. The bootstrap also seeds split files for users who
prefer smaller operational files or already have an older split setup:

- [[file:gtd/projects.org][projects.org]]: active multi-step outcomes.
- [[file:gtd/next.org][next.org]]: standalone next actions.
- [[file:gtd/waiting.org][waiting.org]]: delegated or blocked items.
- [[file:gtd/someday.org][someday.org]]: possible future actions and ideas.
- [[file:gtd/tickler.org][tickler.org]]: date-triggered reminders.
- [[file:gtd/reference.org][reference.org]]: non-actionable GTD reference.

Existing files are never overwritten. Choose compact or split as your
operational style; do not duplicate the same active task in both.

** Clarifying Inbox Items
For each inbox item, ask:

1. Is it actionable?
2. If yes, is it one physical next action or a project?
3. If it takes more than one action, make it a project.
4. If it belongs on a date, move it to calendar.org.
5. If someone else owns it, move it to Waiting.
6. If it is not actionable, keep it as reference, someday/maybe, or delete it.

Decision guide:

- Trash it when it is no longer useful.
- Move it to reference when it may be useful but requires no action.
- Move it to Someday / Maybe when you may want it later but will not
  commit now.
- Move it to calendar.org when it must happen on a specific date or at a
  specific time.
- Move it to Waiting when someone else owns the next move.
- Move it to Next Actions when it is one visible physical action.
- Move it to Projects when it needs more than one action to finish.

** Todo Keywords
Use these states:

#+begin_example
TODO       not yet ready or not yet selected as the next physical action
NEXT       the next visible action you can do
WAITING    delegated, blocked, or waiting for external input
DONE       completed
CANCELLED  intentionally dropped
#+end_example

Keep the keyword set small. Context, energy, area, person, and topic
belong in tags or properties, not in extra TODO keywords.

** Projects
A project is any outcome that needs more than one action. Mark project
headings with the local tag :project:. Child tasks inherit normal topic
and context tags, but :project: itself does not inherit, so agenda
project views stay clean.

This follows Karl Voit's Org project approach: projects stay normal TODO
headings and are marked with :project:, a progress cookie, and recursive
COOKIE_DATA. During migration, older TODO headings with TODO children
are still treated as projects so old data remains visible.

Minimal project example:

#+begin_example
,** TODO [/] Renew driving license :project:admin:
:PROPERTIES:
:CATEGORY: license
:COOKIE_DATA: todo recursive
:END:
,*** NEXT Find required city-office documents :@computer:
,*** TODO Book appointment :@computer:
,*** WAITING Confirmation from city office
#+end_example

The progress cookie [/] and COOKIE_DATA property let Org show project
progress from child task states.

Use C-c g p on a heading to mark it as a GTD project. It adds the local
:project: tag, creates an ID, sets recursive TODO cookie data, and adds
a progress cookie when missing. Use C-u C-c g p when you also want to
set or change CATEGORY.

Every active project should have at least one NEXT child action. If it
does not, it appears in the stuck-project agenda view with C-c a X.

** Subprojects And Links
If a task grows, turn it into a project and link it to its parent
instead of forcing everything into one tree. Use IDs for stable links:

#+begin_example
M-x org-id-get-create
C-c l      ;; store a link
C-c C-l    ;; insert a link elsewhere
#+end_example

Use a normal Org link when two outcomes are related. Use org-edna
properties only when there is a real dependency that should
automatically unlock or block another item.

For related projects or subprojects, prefer org-super-links backlinks:

#+begin_example
C-c g s  ;; search for a heading and create a bidirectional link
C-c g l  ;; store current heading for later super-link insertion
C-c g i  ;; insert the stored super link here
C-c g d  ;; delete a super link and its backlink
#+end_example

To add org-edna dependencies, first create stable IDs on the target
headings, then edit the dependency properties on the heading that owns
the dependency:

#+begin_example
M-x org-id-get-create  ;; create or show the current heading ID
C-c g e                ;; edit BLOCKER/TRIGGER for this heading
M-x my/org-edna-edit   ;; same command by name
#+end_example

Inside the Edna edit buffer, write only the value below the BLOCKER or
TRIGGER section header. Finish with C-c C-c. Completion is available
with M-TAB or the normal completion key.

Dependency sketch:

#+begin_example
:BLOCKER: ids("id:parent-project-id")
:TRIGGER: ids("id:child-action-id") todo!(NEXT)
#+end_example

** Reviews
Daily review:

1. Empty inbox.org into the right lists.
2. Check calendar.org for today and the next few days.
3. Check Waiting for anything that needs a follow-up.
4. Pick realistic NEXT actions for the day.

Weekly review:

1. Review every project.
2. Every active project should have at least one NEXT child action.
3. Review Waiting and Someday / Maybe.
4. Review Tickler items and dated follow-ups.
5. Add or remove horizons, goals, and areas as your life changes.
6. Archive DONE and CANCELLED items that no longer need to stay visible.

Monthly or quarterly review:

1. Review Areas, Goals, and Life / Values.
2. Decide which goals deserve active projects.
3. Delete or demote projects that no longer matter.

* Next Actions
Purpose: standalone NEXT actions that are ready to do. Project-specific
NEXT actions may also live as children of their project. Use this
section for actions that do not need a larger project container.

Good next actions start with a physical verb and usually carry a
context tag such as :@computer:, :@calls:, :@home:, or :@errand:.

Example shape:

#+begin_example
,** NEXT Call city office about required driving-license documents :@calls:
#+end_example

* Projects
Purpose: active outcomes that need more than one action. Use C-c c p to
capture a new project, or C-c g p on an existing heading to mark it as a
project.

Each active project should answer two questions:

1. What finished outcome would make this complete?
2. What is the next visible action?

Split a task into a project as soon as it has hidden steps. If a project
keeps growing, create a subproject and link it with Org ID links.

* Waiting
Purpose: delegated, blocked, or external items where the next move is
not yours. Use WAITING and make the waiting condition visible in the
title, notes, or properties.

During review, decide whether to follow up, keep waiting, convert it
back to a NEXT action, or cancel it.

* Someday / Maybe :someday:
Purpose: possible future actions, ideas, and projects that are not
current commitments. This is not a guilt list. Review it, activate what
matters, and delete what no longer belongs in your life.

* Tickler
Purpose: reminders that should resurface later. Use this for dated
prompts that are not hard appointments. True appointments and fixed
deadlines belong in calendar.org.

When a tickler becomes current, clarify it again: move it to Next
Actions, Projects, Waiting, Someday / Maybe, calendar.org, or delete it.

* Horizons
** Areas :area:
Stable responsibilities you want to maintain, such as health, finance,
family, work, learning, home, friends, and administration.

Areas are maintained, not completed. They should help you notice missing
projects and rebalance attention.

** Goals :goal:
Outcomes above the project level. These should explain why projects matter.

Goals should eventually create or retire projects. If a goal has no
active project for a long time, decide whether it is still real.

** Life / Values :life:
High-level direction, standards, identity, and long-range decisions.

Use this section during slower reviews, not during daily execution.

* Reference Links :reference:
Put links here only when they support GTD reviews. General knowledge
belongs in your normal notes or wiki.
